一、Gaia-X Trust Framework 核心概念

想象你要在一个可信市场里卖能源数据。市场管理方制定了一套规则：

  • 每个卖家必须出示营业执照（LegalParticipant）
  • 每个商品必须有清晰的描述（ServiceOffering）
  • 所有证件必须由认可的机构签发（Trust Anchor）
  • 检查员会验证证件真伪和内容完整性（Compliance Service）

Gaia-X Trust Framework 就是这个"可信市场"的规则手册，定义了在 Gaia-X 数据空间中什么是"可信的"。

Self-Description：Gaia-X 的核心

Self-Description（自描述）是 Gaia-X 的核心概念。它本质上是用 Verifiable Credential 格式编写的实体描述，具备以下特征：

  • 机器可读文本（JSON-LD 格式）
  • 加密签名，防止内容篡改
  • 遵循 Linked Data 原则
  • 格式遵循 W3C Verifiable Credentials Data Model
关键公式

Self-Description = Verifiable Credential + Gaia-X 特定类型（LegalParticipant / ServiceOffering / DataResource）

四种规则类型

规则类型说明谁执行
序列化格式与语法验证 JSON-LD 格式是否正确、context 是否可解析Compliance Service
加密签名验证验证 proof 是否有效、密钥对是否与身份匹配Compliance Service
属性值一致性验证各属性值是否符合定义的数据类型和约束Compliance Service + SHACL
属性真实性验证验证关键声明是否真实（如注册号是否有效）Trust Anchor + 外部验证

三个信任维度

维度含义实现方式
身份信任参与者确实是它声称的那个实体DID + Verifiable Credential + Trust Anchor
合规信任参与者的 Self-Description 符合 Trust Framework 规则SHACL shapes + Compliance Service
数据主权信任数据提供方保持对数据的控制Policy + Contract + Connector

二、模板文件逐字段解析

2.1 LegalParticipant 模板

DSSC_Minimal_Energy_Scenario/gaia-x/legal-participant.template.jsonld

这个模板描述了场景中的 Provider —— Energy Data Provider Ltd. 作为合法参与者的自描述：

{
  "@context": [
    "https://www.w3.org/2018/credentials/v1",
    { "gx": "https://w3id.org/gaia-x/development#" }
  ],
  "id": "https://example.org/dssc-energy/credentials/legal-participant-energy-provider",
  "type": ["VerifiableCredential", "LegalParticipant"],
  "issuer": "did:web:example.org",
  "issuanceDate": "2026-05-01T00:00:00Z",
  "credentialSubject": {
    "id": "did:web:energy-provider.example.org",
    "gx:legalName": "Energy Data Provider Ltd.",
    "gx:legalRegistrationNumber": "DEMO-ENERGY-001",
    "gx:headquarterAddress": { "gx:countrySubdivisionCode": "CN-GD" },
    "gx:legalAddress": { "gx:countrySubdivisionCode": "CN-GD" }
  }
}

字段详解

字段值（模板中）含义与注意点
@contextVC v1 + gx 命名空间必须包含 W3C VC context，Gaia-X 字段通过 gx: 前缀声明
idhttps://example.org/...该 VC 的全局唯一标识符。模板使用 example.org，实际应使用真实可解析 URL
type["VerifiableCredential", "LegalParticipant"]基类必须是 VerifiableCredential，Gaia-X 类型 LegalParticipant 表明这是"合法参与者"描述
issuerdid:web:example.org签发者 DID。模板使用占位符，实际必须是受信任的 Trust Anchor
issuanceDate2026-05-01T00:00:00ZISO 8601 格式签发时间
credentialSubject.iddid:web:energy-provider.example.org被描述的参与者自身的 DID，应与 issuer 不同（除非自签）
gx:legalNameEnergy Data Provider Ltd.法定名称，必填
gx:legalRegistrationNumberDEMO-ENERGY-001注册号。模板使用占位符，实际需符合目标国家格式
gx:headquarterAddress{"gx:countrySubdivisionCode": "CN-GD"}总部地址，至少包含 ISO 3166-2 行政区代码（如 CN-GD = 广东）
gx:legalAddress{"gx:countrySubdivisionCode": "CN-GD"}法定注册地址，格式同 headquarterAddress
模板局限（为什么不一定能通过官方 compliance）
  • 没有真实可解析的 DID document（did:web:example.org 不存在）
  • 没有 cryptographic proof（缺少 proof 字段的数字签名）
  • 没有保证满足当前 Gaia-X Trust Framework 的全部 required fields
  • issuer 不是真实的 Trust Anchor

三、Compliance Service：验证引擎

3.1 核心功能

项目说明
输入参与者提供的 W3C Verifiable Presentations
检查手段使用 Gaia-X Registry 中可用的 W3C SHACL 格式 shapes
输出返回 W3C Verifiable Credential，即带 Gaia-X 签名的 "Gaia-X Compliance Credential"，证明输入已通过所有验证
目的将 Trust Framework 操作化，通过计算和验证策略确保数据主权
附加功能自动化数据空间治理与合规评估：入驻 onboarding、监管约束合规性评估、退出 offboarding
https://toolbox.dssc.eu/?pane=tools&f%5Bquery%5D=Gaia-x+&tool=gaia-x-compliance-service&tool-details=gaia-x-compliance-service

3.2 验证流程（6 步）

Step 1
→
接收 Self-Description（VC/VP 格式）
Step 2
→
验证 proof（签名是否有效、内容是否被篡改）
Step 3
→
验证 issuer（是否在 Trust Anchor 列表中）
Step 4
→
验证 revocation（凭证是否被撤销）
Step 5
→
验证 SHACL（内容是否符合 Trust Framework shapes）
Step 6
→
输出验证报告（通过/失败 + 详细原因）

3.3 验证报告格式

失败示例：

{
  "conforms": false,
  "results": [
    {
      "focusNode": "urn:uuid:.../legal-participant",
      "path": "gx:headquarterAddress",
      "message": "headquarterAddress is required.",
      "severity": "sh:Violation"
    },
    {
      "focusNode": "urn:uuid:.../legal-participant",
      "path": "gx:legalRegistrationNumber",
      "message": "legalRegistrationNumber must match pattern ^[A-Z]{2}-\\d{6,}$",
      "severity": "sh:Violation"
    }
  ]
}

通过示例：

{
  "conforms": true,
  "results": [],
  "credential": {
    "type": ["VerifiableCredential", "GaiaXComplianceCredential"],
    "issuer": "did:web:compliance.gaia-x.eu",
    ...
  }
}

验证报告字段说明

字段含义
conformstrue = 通过，false = 失败
results错误详情数组，通过时为空
focusNode出问题的节点（哪个实体）
path出问题的属性路径（哪个字段）
message人类可读的错误描述
severity严重程度：sh:Violation（必须修复）或 sh:Warning（建议修复）

四、Registry：参考数据存储

4.1 定位与功能

Registry 是一个以去中心化为核心的开源软件，是 Gaia-X 治理的支柱。它存储以下关键信息：

  • Gaia-X Trust Anchors 列表
  • Trust Anchors 验证过程的结果
  • Trust Anchors 身份的潜在撤销信息
  • Gaia-X Verifiable Credentials 的 shapes 和 schemas
https://toolbox.dssc.eu/?pane=tools&f%5Bquery%5D=Gaia-x+&tool=gaia-x-registry&tool-details=gaia-x-registry

4.2 Registry 存储的内容及其对验证的影响

内容格式对 Compliance 验证的影响
SHACL ShapesTurtle (.ttl)定义每种 Self-Description 必须有哪些字段和约束。Compliance Service 用这些 shapes 检查传入的 VC 是否满足结构要求。Shapes 更新时，验证规则同步更新。
Trust AnchorsVC / JSON-LD决定哪些 issuer 被信任。如果 issuer 不在 Trust Anchor 列表中，验证直接失败。这是信任链的起点。
公钥JWK / PEM用于验证 Self-Description 的数字签名。Compliance Service 从 Registry 获取 issuer 的公钥来校验 proof。
撤销列表JSON / Bitstring记录已被撤销的凭证 ID。验证时若发现凭证 ID 在撤销列表中，立即拒绝。
已验证的 SDJSON-LD通过验证的 Self-Description 存档，可供查询。

4.3 技术架构

  • 基于 DNSSEC 和 IPFS
  • 利用 DNS URI/TXT 记录 宣传当前 URI（ipfs:// 链接，内含 CID）
  • IPFS 中存储的数据包括：治理文件、shapes、schemas 及其他关键生态信息

版本名称状态
v1 / v1.x.xGXDCH Tagus早期版本，部署于 Clearing Houses
v2 / v2.x.xGXDCH Loire当前稳定版，部署于 Clearing Houses

五、实战步骤

Step 1：理解模板结构

1仔细阅读两个模板文件，用上面的字段解析表对照每个字段的含义。

  • 打开 legal-participant.template.jsonld，标注每个字段的含义
  • 打开 service-offering.template.jsonld，标注每个字段的含义
  • 画出两个模板之间的引用关系（ServiceOffering.providedBy → LegalParticipant.id）

Step 2：查找官方 Sample Credentials

2对照 Gaia-X 官方 sample credentials，找出模板中可能缺失的 required fields。

https://gaia-x.gitlab.io/policy-rules-committee/trust-framework/gaia-x_trust_framework/
  • 访问 Gaia-X Trust Framework 官方文档
  • 查找官方提供的 LegalParticipant 和 ServiceOffering 的完整示例
  • 对比模板，列出模板缺少但官方要求的字段（如可能缺少的 gx:termsAndConditions.hash 真实值、proof 字段等）

Step 3：构造测试 Credential

3准备两个测试用例：一个故意不完整的（预期失败），一个尽量完整的（观察结果）。

失败样例思路（故意不完整）：

  • 删除 gx:legalRegistrationNumber → 预期失败：缺少必填字段
  • 将 gx:headquarterAddress.countrySubdivisionCode 改为无效值（如 "XX-YY"） → 预期失败：格式不符合
  • 使用不在 Trust Anchor 列表中的 issuer → 预期失败：issuer 不受信任
  • 删除 proof 字段（如果构造时添加过） → 预期失败：缺少签名

完整样例思路（尽量通过）：

  • 基于官方 sample 填充所有 required fields
  • 使用官方 lab instance 认可的 Trust Anchor（或了解 lab 的测试配置）
  • 确保 JSON-LD context 可解析

Step 4：调用 Compliance Service

4使用 curl 或 Postman 调用官方 Compliance Service 或 lab instance。

  • 找到官方 Compliance Service 的 API 端点（如 lab instance 地址）
  • 构造 HTTP POST 请求，Content-Type: application/json
  • 在请求 body 中放入 Verifiable Presentation（包含要验证的 VC）
  • 发送请求并保存响应

示例 curl 结构（需根据实际 endpoint 调整）：

curl -X POST https://compliance.lab.gaia-x.eu/api/v1/credential-offers \
  -H "Content-Type: application/json" \
  -d '{
    "@context": ["https://www.w3.org/2018/credentials/v1"],
    "type": ["VerifiablePresentation"],
    "verifiableCredential": [
      { /* 你的 LegalParticipant VC */ },
      { /* 你的 ServiceOffering VC */ }
    ]
  }'

Step 5：分析验证结果

5记录并分析成功和失败的响应。

  • 保存完整的 HTTP 响应（状态码 + response body）
  • 对失败响应，逐条分析 results 数组中的每项：focusNode、path、message
  • 将错误归类：是签名问题？issuer 问题？SHACL 约束问题？还是格式问题？
  • 对照 Registry 中提供的 shapes，解释为什么某些字段是 required

Step 6：分析 Registry 的影响

6说明 Registry 如何影响验证结果。

  • 若验证失败原因为 "issuer not in trust anchor list"，说明 Registry 的 Trust Anchor 列表起决定性作用
  • 若验证失败原因为 "missing required field: gx:xxx"，说明 Registry 的 SHACL shapes 定义了字段约束
  • 若验证失败原因为 "signature verification failed"，说明 Registry 提供的公钥不匹配
  • 若验证失败原因为 "credential has been revoked"，说明 Registry 的撤销列表生效

八、常见问题

Q1：模板可以直接提交到官方 Compliance Service 吗？

不可以。模板中的 example.org、缺少的 proof、占位符注册号等都会导致验证失败。模板仅用于理解结构。

Q2：如何找到官方 sample credentials？

从 Gaia-X Trust Framework 官方文档（第一个链接）的示例部分查找，或在 Gaia-X GitLab 仓库中搜索 sample credentials。

Q3：Compliance Service 和 Registry 必须一起部署吗？

Compliance Service 依赖 Registry 提供的 shapes 和 trust anchors，但研究阶段可以优先使用官方提供的在线 lab instance，不必本地完整部署。

Q4：B 组需要本地部署 Registry 吗？

第一阶段不要求。优先使用官方 instance 调用 API，理解流程后再评估是否需要本地部署。

Q5：如果 lab instance 返回 500 错误怎么办？

记录完整的请求和响应，分析是网络问题、格式问题还是服务端问题。即使无法成功调用，也要保留错误截图和分析。
